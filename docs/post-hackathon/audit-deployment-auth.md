# Deployment, identity and security audit

Planning evidence captured 2026-11-23 against main `be13793`, on `post-hackathon-plan/changes`. This is a source audit, not a penetration test or a live hosted verification. No private configuration, student content or credentials were inspected. No application changes are proposed as already complete.

## Assessment

The code is a useful local multi-user prototype, with real Supabase JWT verification, scoped queries, RLS, encrypted connector credentials and private file access. It is not ready for an unrestricted public launch. Ship an invite-only, Canvas-first hosted pilot after the P0 gates below; add remote browser connectors only after their separate session architecture is tested. Do not make Gmail permission a condition of app sign-in.

## Identity: correct the assumptions before implementation

UMass's current [Google Workspace page](https://www.umass.edu/it/google-workspace) says Gmail is the official system for undergraduate and graduate students and select faculty/staff; its [Gmail FAQ](https://umass.service-now.com/sp/en/umass-amherst-gmail-f-a-q?id=kb_article_view&sysparm_article=KB0010227) agrees. The older general Workspace FAQ contradicts this for graduate students. Prefer these specific, current sources; the repo's “most likely Microsoft 365” assumption in `docs/02-integrations-and-auth.md` is stale. Faculty/staff email coverage still varies.

“Continue with Google” can authenticate a UMass-managed Google account. It does not give the app a SPIRE session, prove current enrollment, establish instructor privileges, connect Canvas/Gradescope/Piazza, or grant Gmail/Calendar access. University-managed Google login may delegate to the institution's identity provider, but an exact Google → SPIRE → Google route has not been verified. Let Google/university redirects happen normally; never build or promise a custom SPIRE hop or collect NetID passwords.

Existing code: `apps/web/src/lib/auth/supabase-backend.ts:10` creates a PKCE client, and `:26` calls Supabase Google OAuth. `auth/callback/page.tsx` routes to onboarding or Today. The public feature flag only shows the button; it does not configure the Google Cloud client, Supabase provider, redirect allowlist, consent screen or eligibility policy.

Recommended first-pilot identity policy: an explicit invitation allowlist plus verified sign-in identity; decide whether approved personal accounts are allowed. If access is UMass-only, enforce membership using trusted server-side identity information, not a frontend email suffix or user-editable profile metadata. Google's `hd` request parameter is only a chooser hint; its returned ID-token domain claim is the trust signal, as explained in [Google OIDC documentation](https://developers.google.com/identity/openid-connect/openid-connect). Verify how Supabase exposes trusted provider claims before choosing the hook/claim design. Institutionally supported SAML/OIDC SSO is a later UMass IT integration requiring confirmation; no institutional agreement is established by this repo.

Google sign-in should request only identity scopes. [Supabase's Google guide](https://supabase.com/docs/guides/auth/social-sign-in/auth-google) separates Supabase session tokens from Google API tokens and documents offline-access refresh tokens. Store connector refresh tokens separately on the server, encrypted, and request Gmail/Calendar consent only when the user enables that connector. [Google production policy](https://developers.google.com/identity/protocols/oauth2/production-readiness/policy-compliance) requires accurate branding, minimal scopes and applicable sensitive/restricted-scope review. UMass Workspace administrators can also control third-party access; a successful personal-account test does not prove institutional access.

## Proposed deployment design

Use distinct development, staging and production Supabase projects and secrets; never connect fixture tests to production. Keep the existing architecture: Next.js web, a long-lived FastAPI service for SSE, and separate long-lived Procrastinate workers close to managed Postgres/Storage. A managed container host is a suitable category for API/workers; a static/serverless function timeout must not truncate chat or imports. Avoid choosing a vendor before measuring memory, browser/extraction needs, connection limits and monthly budget.

Web and API use explicit HTTPS origins, secure callback allowlists, private storage and managed secrets. Pin runtime versions and lockfiles. Configure proxy streaming/no buffering, request cancellation, graceful draining, deployment version headers and bounded timeouts. Keep durable work in the database/queue, not web process memory. Model/provider outages should produce an honest retryable state while deterministic Today data remains usable.

For Gradescope/Piazza, choose one separately reviewed option: isolated remote browser sessions with short-lived owner-bound live views, no recordings/password logging and encrypted session export; a user-installed local helper/extension with explicit permissions; or institution/vendor-supported access. The latter is preferable long term. A remote browser still handles sensitive sign-in traffic even if the app never stores passwords; privacy copy must describe that honestly. Confirm platform terms, institutional policy and technical feasibility before promising unattended hosted access.

Keep the first product boundary student-private. A professor using the app may see their own sources; instructor-wide/student-roster access, sharing and analytics need separate roles, authorization rules, consent/data-governance review and tests. Never infer a professor role from an email address alone.

## Implementation sequence and acceptance tests (future work)

1. **Identity/config gate.** Production validation, Google Cloud/Supabase setup, separate projects, invite eligibility, exact issuer and safe callbacks. Tests: wrong-domain/uninvited user denied at server, expired/replayed callback/state, account-linking collision, sign-in cancellation, token/key rotation, no fallback demo mode. Controlled manual staging check with one real UMass account and a personal Google account; no password fixtures.
2. **Isolation/deletion gate.** Add auth-transition cache regression and idempotent deletion/fencing. Tests: two users across every data surface; inflight query returns after sign-out; live job resumes after deletion; partial Storage failure retries; old feed revoked; disconnected credential cannot restart work. Use synthetic accounts only.
3. **Deployable artifacts/CI.** Pin builds, DB/storage setup migrations, run integration/RLS/E2E/build checks, stage immutable artifacts, smoke SSE/citations/import/readiness under the production proxy. Test rolling restart, worker crash, DB unavailability, queue backlog and forbidden origins. Prove migration forward/rollback or documented roll-forward recovery without dropping real data.
4. **Operational pilot gate.** Shared request/spend limits, metrics/alerts, health/readiness, key rotation and object+DB restore drill; failure/load tests with synthetic files/users. Publish privacy/retention/deletion/AI-data-use explanations and name support/incident owners.
5. **Hosted connector gate.** Approve architecture/policy first, then implement saved-session isolation and hosted browser lifecycle. Tests: cross-user live-view denial, reconnect/timeout/cancel, container restart, two API instances, no recordings/secrets in logs, expired session, Duo user handoff. Start with small invited cohorts and pause a connector independently when it breaks.

## Decisions needed from the team

- Private invited pilot or unrestricted signup? Which verified UMass identities, alumni and personal Google accounts are eligible?
- Who owns Google Cloud/Supabase/hosting, domain, support email, billing and incident response? What monthly cap and data region?
- Can the first hosted release be Canvas + private calendar while remote Gradescope/Piazza is gated, or must hosted browser login be launch-critical?
- What is the retention/deletion policy, and may course/mail data be sent to the selected model provider under its current terms?
- Are professors initially ordinary private users, or is an institutional multi-role product intended? The second scope needs a separate design.
