## What to retain

- Canvas has an explicit GET-only transport and same-host guard (`canvas/client.py:51–70`); guided setup already exists (`connect/canvas-step.tsx:83`). Never ask for a Canvas password. A PAT may permit writes even though our transport refuses them: describe our app's read-only behavior precisely.
- Gradescope and Piazza reuse sessions without calling password login. Saved browser state is encrypted before storage (`browser/store.py:21`). The assistant does not receive these credentials.
- Piazza has bounded newest-post fetching, current-term filtering and unchanged-post skips (`piazza/connector.py:96`). Saved-session expiry maps to reconnect. The normalizer and original URLs already support the storage/citation path.
- Existing public/private source access must stay per student; a professor role must not inherit access to students' private grades, mail, chats or files merely by connecting the same course.

## Target student flow (proposal)

1. **Sign in** with Google identity, requesting only identity information. Explain whether access is invitation-only or UMass-verified. A Google sign-in does not automatically grant LMS, Gmail or Calendar access.
2. **Choose what you use:** check Canvas, Gradescope, Piazza, optional Gmail, optional calendar; show capability and availability labels. Support “Set this up later.” Do not ask users to type platform passwords into our app, support chats or forms.
3. **Connect each selected source** through its proper consent/token flow. Explain data categories, refresh expectations, disconnect/delete behavior and why access is needed before opening the provider. Show one clear action for an expired login.
4. **Choose classes after discovery.** Display current semester plus “Other terms”; allow selecting active courses and mapping equivalent course links. Add a short source preview and confirm which classes are imported. The discovery API must not import every file before course selection; retained discovery metadata must be bounded and user-scoped.
5. **Choose calendar direction:** “See deadlines in my calendar” (outbound subscription), “Use my calendar to find study time” (availability access), or “Create approved sessions in a study calendar” (separate write consent). Default all optional capabilities off.
6. **Show readiness** per source/class: connected, importing, ready, reconnect needed, limited support. Enter Today while supported sources import. A failed optional source must not block all onboarding.
7. **Settings → Sources and classes** supports add/remove source, course inclusion changes, reconnect, explicit retained-data deletion, and separately revoking Google feature grants. All progress/preferences come from server state; localStorage can cache presentation only.

Proposed internal state: source capability catalog; user-selected integrations and courses; provider subject/account label; granted scopes and consent version; encrypted refresh grant; expiry/revocation state; per-resource sync cursors/watch leases; import policy. These need a contract proposal and team review before migrations. Keep identity login separate from data grants; do not equate matching email addresses with authorization to merge accounts.

## Hosted Gradescope/Piazza choices

| Option | Tradeoff | Recommendation |
|---|---|---|
| Official institution/vendor OAuth/LTI or approved integration | Best long-term permissions and browser UX; availability/access agreement is unverified for this project. | Investigate with UMass IT/vendor before a public promise; LTI access and student-level account access are distinct scopes. |
| Isolated remotely streamed browser per login | Can preserve interactive school login and Duo, but the browser operator holds the authentication environment and resulting session. Requires isolation, TLS access binding, no recordings/key logging, strict timeouts, cleanup, resource limits, durable login orchestration, abuse controls and explicit disclosure. SSO providers may reject hosted browsers. | Bounded feasibility/security review first; never describe this as a simple production toggle. Do not capture or store passwords or bypass MFA. |
| Local companion/extension | Uses the student's browser but introduces installation, sensitive permissions, distribution and support burden. | Conflicts with the current “nothing to install” product rule; needs an explicit product decision, not a silent workaround. |
| Launch Canvas-only, defer session connectors | Narrower initial product; preserves deployability while access is resolved. | Preferred fallback for an invite-only deployment if hosted login cannot be approved. Keep working local demo separate. |

The source code shows public read methods in the Piazza wrapper, but its underlying session transport is general-purpose (`piazza/_vendored/client.py:81`). Add a transport-level read-operation allowlist, redirect validation and tests before making a stronger production security claim. Piazza's current incremental cursor is one connection timestamp (`piazza/connector.py:103`); a newly joined class with old posts can be skipped after a previous successful sync. Plan per-class bootstrap/cursors and a deliberate bounded reconciliation path; do not change the spec silently.

## Gmail design and gates

For mailbox content the candidate is `gmail.readonly`; metadata-only access cannot support body-grounded answers, and both `gmail.readonly` and `gmail.metadata` are **restricted** scopes. Google requires restricted-scope verification and a security assessment when restricted data is stored or transmitted through servers. Do not request send/modify/delete scopes. A user-selected label limits our import policy, not the breadth of the OAuth permission itself. The Gmail add-on current-message scopes are narrower alternatives for a different, user-invoked add-on product, not a silent substitute for background mailbox ingestion. [Google Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes).

Treat Gmail as a later controlled release gate, while starting consent-screen/domain/privacy work early. Use separate encrypted grants, offline access, account binding, scope validation, CSRF state, one-use callback transactions, revocation and token-refresh concurrency controls. Google's web-server flow supports offline access and incremental consent; denied or partial grants must leave identity login working. [Google OAuth web-server flow](https://developers.google.com/identity/protocols/oauth2/web-server).

Start with a user-chosen class-mail label and a bounded recent window; preview retained categories; do not ingest the entire historical inbox by default. Parse plain text safely, exclude remote images and attachments initially, retain Gmail message/thread IDs and source permalinks, and isolate all retrieval by owner. Email content is untrusted prompt data. Mail-derived suggested deadlines remain distinct from authoritative LMS due dates until confirmed. Store only necessary sender information and provide per-source deletion and retention controls.

For efficient updates, use Gmail Pub/Sub notifications to enqueue idempotent history reconciliation, not to put mail content directly into the assistant. Persist a history cursor only after successful processing. Renew watches daily (required at least every seven days), deduplicate delivery, and run periodic reconciliation because notifications can be delayed or dropped. [Gmail push guide](https://developers.google.com/workspace/gmail/api/guides/push). Expired history produces HTTP 404 and needs a bounded fresh bootstrap; history retention is not guaranteed indefinitely. [Gmail sync guide](https://developers.google.com/workspace/gmail/api/guides/sync). Measure quota units per user/project and retry rate-limit failures with jitter rather than assuming a flat request allowance. [Gmail usage limits](https://developers.google.com/workspace/gmail/api/reference/quota).

Before mail reaches any model provider, select contractual no-training/data-handling terms and confirm the intended feature fits Google's permitted use and transfer rules. Google restricts using Workspace data for general model training beyond the specific user's personalized use case; user consent alone is not a substitute for provider compliance. No mail in traces, analytics, shared evaluation corpora or support dashboards by default. [Workspace user-data policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy).

## Calendar: four different features

| Capability | Direction / credentials | Proposed scope and behavior |
|---|---|---|
| Existing private ICS subscription | App → Google/Apple/Outlook; bearer URL, no Google OAuth | First deployable calendar feature. Serve stable HTTPS, preserve UID/SEQUENCE and timezones, protect secrets at proxy/CDN/log layers, and explain provider-controlled refresh. Rotating a URL prevents future fetches but cannot erase already imported copies. |
| ICS file upload | File snapshot → app | Optional bounded import. Label “snapshot,” support replace/remove and UID-based deduplication; it cannot dynamically update itself. Google's import documentation explicitly distinguishes import from continued sync. [Google import help](https://support.google.com/calendar/answer/37118?hl=en). |
| Subscribed ICS URL, including a published Apple/iCloud feed | External feed → app; secret URL | Separate new connector. Poll with ETag/Last-Modified and jitter; store encrypted URL, bound size/time/recurrence expansion, support UID+RECURRENCE-ID changes, cancellations, timezone/all-day events. Strict SSRF defenses: scheme/host/IP validation, DNS/redirect revalidation, no metadata/private networks, egress controls. Never require publishing a private personal calendar without explaining who can read the link. |
| Google Calendar OAuth | Google → app availability/events; optionally app → Google approved writes | Offer permissions by feature. Availability may use FreeBusy rather than titles/descriptions. Candidate event-read scopes are `calendar.events.readonly` plus calendar-list read access if selection is needed. For writing, prefer a dedicated app-created study calendar and evaluate `calendar.app.created` rather than all-calendar write access. No background unapproved study writes. [Google Calendar scopes](https://developers.google.com/workspace/calendar/api/auth). |

Apple supports URL subscriptions and configurable refresh; these are read-only views controlled by the feed provider. Adding our feed to Apple does not grant our server access to a person's other Apple calendars. [Apple subscription guide](https://support.apple.com/en-ca/guide/calendar/icl1022/mac).

For Google read synchronization, persist calendar-level cursors and handle invalid tokens (410) through rebootstrap of that source, preserving unrelated calendars. [Calendar incremental sync](https://developers.google.com/workspace/calendar/api/guides/sync). Watch channels require HTTPS, expire without automatic renewal, and notifications are hints requiring a subsequent read; renew with overlap/deduplication and authenticate channel metadata before enqueuing. [Calendar push guide](https://developers.google.com/workspace/calendar/api/guides/push). Exact sensitive-scope verification requirements must be confirmed for the chosen scopes in Google Cloud before launch; do not bundle Calendar with the Gmail restricted-scope assessment automatically.

Approved Google writes need durable outbox state and idempotency: approval records the exact event/time/calendar, the worker creates or updates only that approved event, and retries cannot duplicate it. Define whether source deadline changes update app-owned events automatically and disclose that policy; attendee invitations and edits to personal events remain out of scope. Keep outbound ICS and OAuth exports from creating duplicate deadline sets.
